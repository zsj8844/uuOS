  └──────┬───────┘                 └──────┬───────┘           └──────┬───────┘
         │                                │                          │
         │ Domain=0x01                    │ Domain=0x02              │ Domain=0x01
         │ HMAC(MK_CTRL)                  │ HMAC(MK_DATA)            │ HMAC(MK_CTRL)
         │                                │                          │

         │   Kernel_WriteTask  │          │   Kernel_ReadTask   │    │   Kernel_ReadShake  │
         │   刻录任务到Sector  │          │   回读任务令牌      │    │   挑战码解锁状态机  │
         │   1024              │          │                     │    │                     │

         │                     │          │   Kernel_WriteData  │    │   Kernel_ReadData   │
         │                     │          │   AES加密落盘       │    │   纯密文盲泵回传    │

  Phase 0: 任务预授权               Phase 1: 现场鉴权+加密吸数        Phase 3: 特权挑战+密文泵出

  握手方向 (每次插入):
  [STM32] ──Hello(Domain, nonce_dev)──▶ [EXE]
  [STM32] ◀──Handshake(nonce_host, HMAC)── [EXE]

| EXE | 运行环境 | 持有密钥 | Domain | 触发 SVC | 固件内核函数 |
|---|---|---|---|---|---|

| **Agent.exe** | 工控现场 PC | MK_DATA | 0x02 | `0x11`, `0x12` | `Kernel_ReadTask`, `Kernel_WriteData` |
| **MasterRecover.exe** | 密网总部 PC | MK_CTRL | 0x01 | `0x19`, `0x1A` | `Kernel_ReadShake`, `Kernel_ReadData` |

## 二、三 EXE 共用的通信架构

### 2.1 物理层：USB Custom HID

三个 EXE 均通过 **USB Custom HID** 协议与 STM32 通信，而非标准 MSC（大容量存储）或 CDC（虚拟串口）。理由：

- HID 无需驱动签名，Windows 免驱即插即用
- 不暴露文件系统，操作系统不会弹出"格式化磁盘"对话框
- 64 字节/包的固定帧长，天然防缓冲区溢出

### 2.2 帧格式定义（64 字节 HID Report）

```
┌────────┬────────┬──────────┬─────────────────────────────────────┬──────────┐
│ Byte 0 │ Byte 1 │ Byte 2-3 │ Byte 4-59 (56 bytes)               │ Byte 60-63│
│ Domain │  Cmd   │  SeqNum  │ Payload                             │  CRC-32   │
│ 0x01/02│ 0x10~  │ (大端)   │ (不足 56 字节时补 0x00)              │ (大端)    │
└────────┴────────┴──────────┴─────────────────────────────────────┴──────────┘
```

| 字段 | 偏移 | 长度 | 说明 |
|---|---|---|---|
| Domain | 0 | 1 | `0x01` = 密网，`0x02` = 工控 |
| Cmd | 1 | 1 | SVC 立即数，即 `0x10`/`0x11`/`0x12`/`0x19`/`0x1A` |
| SeqNum | 2 | 2 | 序列号（大端），防重放，每包递增 |
| Payload | 4 | 56 | 有效载荷，由当前会话密钥 SK 加密（AES-128-GCM 时含 16 字节 Auth Tag 内嵌） |
| CRC-32 | 60 | 4 | 全帧 CRC-32 校验（大端） |

### 2.3 会话密钥派生（三 EXE 通用逻辑）

```
SK = HMAC-SHA256(MK, nonce_dev || nonce_host)

其中:
  MK       = MK_CTRL (密网) 或 MK_DATA (工控)，预烧录在 STM32 安全存储和 EXE 本地密钥文件
  nonce_dev = STM32 生成的 16 字节随机数
  nonce_host = EXE 生成的 16 字节随机数
  SK       = 取前 16 字节作为 AES-128 密钥
```

### 2.4 握手的通用三阶段序列（STM32 设备主动发起）

STM32 作为 USB Device，插入后**主动发出 Hello 帧**宣告身份。EXE 作为 USB Host，启动后在后台轮询等待设备 Hello，不主动发起握手。

```
[STM32] ──Hello(Domain, nonce_dev)────▶  [EXE]   // 设备插入, 主动宣告身份 + 发送 nonce
        ◀──Handshake(nonce_host, HMAC)──         // EXE 收到 Hello, 生成 nonce_host
                                                  // HMAC = HMAC-SHA256(MK, nonce_dev || nonce_host)
                                                  // STM32 独立计算 HMAC 比对验证
        ──HandshakeACK────────────────▶          // 验证通过，双方各自派生 SK

        ◀──Cmd(Cmd=SVC号, Payload=SK加密)──      // 后续指令由 EXE 发起, SK 加密隧道传输
```

**关键设计决策：**

| 决策 | 理由 |
|---|---|
| STM32 先发 Hello | USB Device 自然模型；nonce_dev 由设备熵源生成，主机不可预测 |
| EXE 被动等待 | EXE 启动后即进入后台轮询，设备插入时自动触发握手，无需用户操作 |
| 三次握手 | Hello(设备) → Handshake(主机) → ACK(设备)，共 3 帧完成双向认证 |
| 握手超时 | EXE 发送 Handshake 后等待 ACK 超时 3 秒，超时则断开重连 |

### 3.3 核心流程

```
┌─ 后台等待阶段 (EXE 启动后持续运行) ─────────────────────┐
│ 1. 启动 USB HID 设备监听线程                              │
│ 2. 轮询等待 VID/PID 匹配的 STM32 设备插入                  │
│ 3. 设备插入 → 等待 STM32 主动发送 Hello 帧                 │
│ 4. 收到 Hello(Domain=0x01, nonce_dev[16])               │
│    → 域识别: 密网侧, 加载 MK_CTRL                         │
│    → 提取 nonce_dev                                       │
│ 5. 生成 nonce_host (16 bytes, 密码学安全随机数)            │
│ 6. 计算 HMAC = HMAC-SHA256(MK_CTRL, nonce_dev || nonce_host) │
│ 7. 发送 Handshake(nonce_host, HMAC) → 等待 ACK            │
│ 8. 收到 HandshakeACK → 握手成功                           │
│ 9. 派生 SK1 = HMAC-SHA256(MK_CTRL, nonce_dev || nonce_host)[:16] │
│    → GUI 更新: "握手完成, 可以下发任务"                      │
└──────────────────────────────────────────────────────────┘

┌─ 用户操作阶段 ─────────────────────────────────────────┐
│ 10. 管理员填写任务配置表单                               │
│ 11. 点击 [下发任务到U盘]                                 │
│ 12. 构造任务结构体 TaskPayload:
   ┌────────────┬──────────┬──────────┬─────────┬──────────────┐
   │ valid_from  │ valid_to │ targetID │ strategy│ data_points.. │
   │ (4 bytes)   │ (4 bytes)│ (32B str)│ (1 byte)│ (变长, ≤ N)   │
   └────────────┴──────────┴──────────┴─────────┴──────────────┘

13. 加密: encrypted_payload = AES-128-GCM(SK1, TaskPayload)
14. EXE 发送: Domain=0x01 | Cmd=0x10 | Seq=N | encrypted_payload | CRC32
    → STM32 解密后触发 SVC 0x10 → Kernel_WriteTask → 写入 Sector 1024
15. STM32 回复 ACK → EXE 显示"下发成功, 可拔出U盘"
16. 设备拔出 → EXE 销毁 SK1, 回到后台等待下次插入
```

### 3.4 关键技术点

| 项 | 方案 |
|---|---|
| **USB 通信库** | Windows: `HidLibrary` (NuGet)，后台线程 `ReadFile` 阻塞等待 STM32 的 Hello 帧 |
| **握手方向** | STM32 主动发 Hello，EXE 被动响应；EXE 启动后即进入后台轮询，不主动探测 |
| **GUI 框架** | WinForms (.NET 6) 或 WPF，窗体 600×500 |
| **HMAC-SHA256** | `System.Security.Cryptography.HMACSHA256` |
| **AES-128-GCM** | `System.Security.Cryptography.AesGcm` |
| **密钥存储** | `mk_ctrl.key` 文件 (32 字节二进制)，放 EXE 同目录，不可硬编码 |
| **任务结构体序列化** | 自定义二进制打包 (参考上述格式)，或用 MessagePack |

### 4.3 核心流程

```
阶段 A: 握手 + 读任务 (SVC 0x11)
──────────────────────────────────
1. Agent.exe 启动后进入后台托盘, 轮询等待 STM32 设备插入
2. STM32 插入 → 主动发送 Hello(Domain=0x02, nonce_dev[16])
   → Agent 识别域: 工控侧, 加载 MK_DATA
3. Agent 生成 nonce_host, 计算 HMAC-SHA256(MK_DATA, nonce_dev || nonce_host)
4. Agent 发送 Handshake(nonce_host, HMAC)
5. STM32 验证通过 → 回复 HandshakeACK
6. 双方各自派生 SK2 = HMAC-SHA256(MK_DATA, nonce_dev || nonce_host)[:16]

7. Agent 构造读任务请求, SK2 加密
8. Agent 发送: Domain=0x02 | Cmd=0x11 | Seq=N | encrypted_req | CRC32
   → STM32 解密后触发 SVC 0x11 → Kernel_ReadTask → 读 Sector 1024
9. STM32 回复 TaskToken → Agent 解密得到任务数据

10. 本地 verify_task_policy(TaskToken):
    - 检查当前时间 ∈ [valid_from, valid_to]?
    - 检查 targetID == 本机标识?
    - 检查策略参数合法?
    → 通过: 解锁采集通道, GUI 显示"策略校验通过"
    → 失败: 弹窗告警, 拒绝写入, 等待拔出


阶段 B: 采集 + 推流 (SVC 0x12)
──────────────────────────────────
11. 根据任务中的 data_points 从 PLC/OPC 读取原始数据 raw[]

12. 构造 DataPayload (每包 ≤ 48 字节有效载荷, 为 GCM 留空间):
    ┌────────────┬──────────┬──────────┬──────────────────┐
    │ task_id    │ seq_inner│ timestamp│ raw_data_slice   │
    │ (4 bytes)  │ (4 bytes)│ (8 bytes)│ (≤32 bytes)      │
    └────────────┴──────────┴──────────┴──────────────────┘

13. 加密: encrypted = AES-128-GCM(SK2, DataPayload)
14. Agent 发送: Domain=0x02 | Cmd=0x12 | Seq=N | encrypted | CRC32
    → STM32 解密外层得到 inner
    → Kernel_WriteData 用 MK_DATA 做内层 AES 原位加密
    → sd_raw_write_sector() 落盘 Sector 1025+
15. 循环 11~14 直到数据全部推送完毕
16. Agent 发送 EOF 帧 (Cmd=0x12, Payload=全零) → STM32 状态机闭锁 STATE_LOCK
17. 设备拔出 → Agent 销毁 SK2, 回到后台等待下次插入
```

### 4.4 关键技术点

| 项 | 方案 |
|---|---|
| **USB 通信** | 后台线程阻塞等待 STM32 Hello 帧，不主动探测设备 |
| **握手方向** | STM32 主动发 Hello，Agent 被动响应 |
| **PLC/OPC 数据采集** | 根据工控环境使用 Modbus TCP/RTU 库 (如 NModbus4) 或 OPC-UA SDK |
| **运行模式** | 支持系统托盘后台运行，U盘插入时 STM32 发 Hello → 自动弹窗握手 |
| **策略校验** | 纯本地运算，不依赖网络，断开气隙也能工作 |
| **密钥存储** | `mk_data.key` 文件 (32 字节二进制)，权限设为仅当前用户可读 |

### 5.3 核心流程

```
阶段 A: 握手 + 特权挑战 (SVC 0x19)
──────────────────────────────────
1. MasterRecover.exe 启动后轮询等待 STM32 设备插入
2. STM32 插入 → 主动发送 Hello(Domain=0x01, nonce_dev'[16])
   → 识别域: 密网侧, 加载 MK_CTRL
3. (全新 nonce, 与前次 SK1 无关, 会话完全隔离)
4. MasterRecover 生成 nonce_host', 计算 HMAC-SHA256(MK_CTRL, nonce_dev' || nonce_host')
5. MasterRecover 发送 Handshake(nonce_host', HMAC)
6. STM32 验证通过 → 回复 HandshakeACK
7. 双方各自派生 SK1' = HMAC-SHA256(MK_CTRL, nonce_dev' || nonce_host')[:16]

8. MasterRecover 生成特权挑战码 challenge = random(32 bytes)
9. 构造挑战请求: AES-128-GCM(SK1', challenge)
10. MasterRecover 发送: Domain=0x01 | Cmd=0x19 | Seq=N | encrypted_challenge | CRC32
    → STM32 解密后触发 SVC 0x19
    → Kernel_ReadShake 验证挑战码
    → 通过: 状态机解锁 STATE_READ_ALLOW
    → 失败: 拒绝, 累计 3 次失败 → STATE_CORE_PANIC
11. STM32 回复 ACK → 挑战成功, GUI 显示 "读权限已解锁"


阶段 B: 可选查询 (复用 SVC 0x1A 查询模式)
──────────────────────────────────
12. MasterRecover 发送查询请求: Cmd=0x1A, Payload=0x00 (查询模式标志)
13. STM32 回复密文 ID 列表: [{task_id, timestamp, size_bytes}, ...]
14. 操作员在 GUI 中选择需要回收的数据


阶段 C: 密文泵出 + 本地解密 (SVC 0x1A)
──────────────────────────────────
15. MasterRecover 构造抽取请求 (含目标 task_id 列表), SK1' 加密
16. MasterRecover 发送: Domain=0x01 | Cmd=0x1A | Seq=M | encrypted_request | CRC32
    → STM32 解密后触发 SVC 0x1A
    → Kernel_ReadData 调用 sd_raw_read_sector(Sector 1025+)
    → 原始 inner 密文 (MK_DATA 加密态) 原样泵出

17. 循环接收密文扇区数据:
    ┌─────────┬────────────────────────────────┐
    │ Seq=N   │ inner_ciphertext (512 bytes)    │
    └─────────┴────────────────────────────────┘

18. 全部接收完毕, MasterRecover 发送 EOF
19. 本地解密: raw = AES-128-GCM-Dec(MK_DATA, inner)
20. 拼装原始日志文件, 写入本地磁盘
21. 设备拔出 → MasterRecover 销毁 SK1', 回到后台等待
```

### 5.4 本地解密模块

```
host_decrypt_file(input: encrypted.dat, output: recovered.log):

  MK_DATA = read_key_file("mk_data.key")

  for each 512-byte sector_block in input:
      nonce = sector_block[0:12]
      tag   = sector_block[496:512]
      ct    = sector_block[12:496]

      plain = AES-128-GCM-Dec(MK_DATA, nonce, ct, tag)
      write(output, plain)

  verify_crc(output)  // 可选完整性校验
```

### 5.5 关键技术点

| 项 | 方案 |
|---|---|
| **USB 通信** | 后台线程阻塞等待 STM32 Hello 帧，不主动探测设备 |
| **握手方向** | STM32 主动发 Hello (全新 nonce)，MasterRecover 被动响应 |
| **挑战码生成** | `RandomNumberGenerator.GetBytes(32)` — 密码学安全随机数 |
| **防暴力保护** | 3 次挑战失败 → 固件进入 STATE_CORE_PANIC，密钥自毁 |
| **本地解密** | 主机端算力充足，AES-128-GCM 软件解密速度 > 50 MB/s |
| **输出路径** | 用户可配置默认路径 `C:\Recovery\`，文件名含时间戳 |
| **密钥文件** | `mk_data.key` 由管理员从 HSM 导出，权限严密管控 |

## 六、三 EXE 对比总结

| 维度 | MasterTask.exe | Agent.exe | MasterRecover.exe |
|---|---|---|---|
| **环境** | 密网总部 | 工控现场 | 密网总部 |
| **密钥** | MK_CTRL | MK_DATA | MK_CTRL + MK_DATA |
| **Domain** | 0x01 | 0x02 | 0x01 |
| **SVC 触发** | 0x10 | 0x11, 0x12 | 0x19, 0x1A |
| **数据方向** | PC→U盘 (写入) | PC→U盘 (写入) | PC←U盘 (读取) |
| **数据量** | ~100 字节 (任务令牌) | MB~GB 级 (日志流) | MB~GB 级 (密文流) |
| **GUI** | 完整窗体 | 精简托盘式 | 完整窗体 |
| **关键操作** | 配置任务 → 一键下发 | 自动握手 → 读令牌 → 校验 → 采集推流 | 挑战解锁 → 密文泵出 → 本地解密 |
| **安全要求** | 操作员身份认证 | 全自动无人值守 | 操作员身份认证 + 审计日志 |

## 七、开发阶段建议

### 第一阶段：无加密透传验证（当前 Demo 就绪后）

1. 实现 USB Custom HID 双向通信（固件侧 + PC 侧）
2. 固件 STM32 能主动发送 Hello 帧，三个 EXE 能接收 Hello 并回复 Handshake、接收 ACK
3. 能发送 Cmd 字节，固件侧 SVC_Router 正确分发并闪灯
4. 暂不实现 HMAC 和 AES，Payload 明文透传

### 第二阶段：加入 HMAC 握手

1. 固件侧实现 `sec_audit_packet()` 的 HMAC 验证逻辑
2. EXE 侧实现 HMAC 签名和 SK 派生
3. 验证握手成功 → 后续指令正常；握手失败 → 固件拒绝

### 第三阶段：全链路加密

1. 固件侧接入 AES-128-GCM（软件实现或硬件加速）
2. 指令和 Payload 均在 SK 加密隧道中传输
3. 工控侧双层加密验证（SK2 外层 + MK_DATA 内层）

### 第四阶段：完整集成 + 压力测试

1. GB 级数据持续推流 + 加密落盘 + 回读解密
2. 异常注入测试（中途拔 U 盘、坏扇区、挑战失败 3 次）
3. 跨 Windows 版本兼容性验证

## 八、关键技术决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| USB 协议 | Custom HID | 免驱、无文件系统暴露、64 字节固定帧 |
| 握手机制 | HMAC 挑战-应答 | STM32F103 毫秒级完成，无需 ECDHE 算力 |
| 对称加密 | AES-128-GCM | 同时提供加密和完整性校验，单程完成 |
| 密钥长度 | 128-bit (16 bytes) | STM32F103 软件 AES-256 开销过大，128 位对原型足够 |
| GUI 框架 | .NET 6 WinForms | 开发快、HID 库成熟、Windows 原生支持 |
| 固件端加密 | 软件实现 (mbedTLS 裁剪) | STM32F103 无硬件 AES，裁剪 mbedTLS 仅保留 AES-GCM + SHA-256 |
